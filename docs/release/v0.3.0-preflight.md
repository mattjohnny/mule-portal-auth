# v0.3.0 release preflight

Use this checklist to release `@mule/portal-auth` v0.3.0, from the first data check to fleet
adoption. The release is cut from `main` after both PR #10 (request authority) and the
release-gate PR for issue #11 have merged. `package.json` says `0.2.4` until the release PR
changes it. Tracking issue: mattjohnny/mule-portal-auth#11.

Complete the sections in order. Tag only at the end of section 4, because its cross-repo
proofs bind to the release commit's SHA. No consumer adopts the tag before then.

## 1. Version and release notes

### Why 0.3.0, not 0.2.5

`readAppDirectory()` returned `Promise<unknown>` in v0.2.4 and at `57c199b`. It now returns a
validated `Promise<PortalAppDirectory>`. This breaks a TypeScript consumer that compiled
against 0.2.4. Accountability's `await auth.readAppDirectory() as Record<string, unknown>`
(`src/auth.ts`) fails `tsc` with TS2352 against the new type. Workback passes the result to a
`(directory: unknown)` parameter, so it still compiles. In a 0.x package, a breaking change
takes the next minor version.

### Release-note items

1. **`readAppDirectory()` type and runtime change.** It now takes
   `{ include_non_mule?: boolean }` and returns `PortalAppDirectory`. Every call fetches with
   `cache: "no-store"`. The connector rejects, with `PortalError`, a directory that has missing
   fields, duplicate or contradictory people or locations, a non-Mule location the caller did
   not ask for, or a `syncedAt` outside a 30-second clock-skew window. No saved directory is
   used as a fallback. Accountability must remove its cast (section 5).
2. **Request authority mode.** `authorityMode: "request"` is opt-in for `createPortalAuth`
   and `createPortalAuthAsync`. Each protected request makes its own Portal lookup and never
   saves the result. Request mode requires an explicit app grant even for ops, and refuses
   offline and dev fallback. Each protected request is one Portal call. Since
   mule-portal#122 (`bc353a7`), each authenticated app has its own allowance of 60 Portal
   calls a minute (README, "Request authority"). Confirm that the app's peak rate fits
   before any request-mode pilot.
3. **Stricter validation in cached mode too.** Present claims are now checked more strictly
   than in v0.2.4:
   - Emails must match `^[^\s@]+@[^\s@]+$`.
   - `roles` must start with the primary role, followed only by `finance` or `hr`, each at
     most once (PR #13). The Portal stores only `finance` today.
   - Every `app_permissions` key must be one of `apps`.
   - `apps` and permission lists must be trimmed, non-empty and unique.
   - Location keys must have no leading or trailing whitespace, and no location list may
     repeat an id or a key.
   - `ctx_version` must be a safe integer.

   Portal data that v0.2.4 accepted can now refuse a sign-in, a re-check or a whole directory
   read (section 2).
4. **HTTPS-only Portal transport for apps still on v0.2.4.** The C2 changes (PR #7, `57c199b`)
   are new to every app pinned to tag v0.2.4 (`c09be12`). A Portal request fails locally,
   with `PortalError.unavailable === false`, unless its URL is HTTPS whenever
   `NODE_ENV=production` or `RENDER` is set. Redirects are never followed for SSO, context,
   directory or credential-proof requests. Accountability, pinned to `57c199b`, already has
   these changes.

### Behaviour changes in this release

1. **Back-off:** on a Portal `429` or `503` with a whole-seconds `Retry-After`, `requireAuth`
   and `requireAdmin` send it on their `503`, clamped to 1–300 (otherwise 5). A `429` is still
   not an outage, and nothing retries.
2. **Dev sign-in:** `devSignIn` throws a `PortalError` in request mode and creates no session.
3. **Session expiry:** a session with a revalidation handle expires after
   `min(sessionTtlMs, 8 h)`. Sessions without one keep `sessionTtlMs` (default 8 h).
4. **Log names:** denial logs say `error_name: "PortalError"` or `"PortalCredentialError"`
   instead of `"Error"`, and still never include a message.
5. **Request context:** `getContext`, `locationIds` and `locationKeys` prefer the request's
   own `req.portal` over any `req.context` that other middleware set.
6. **Revalidation identity:** re-checks use the stored session row's email and handle, not
   the caller's `Session` object. This includes the offline-admin email check.
7. **Mode check:** `auth.authorityMode` (read-only, type `PortalAuthorityMode`) reports the
   validated mode. HR should assert `"request"` at boot.
8. **Directory errors:** a refused `readAppDirectory()` still fails as a whole. Its
   `PortalError.detail` names only the failed check and position (such as `people[3].email`),
   never a value, so it is safe to log.
9. **Unadmitted requests:** for a request that has not passed `requireAuth` (no
   `req.portal`), `getContext` returns `null` and `locationIds` and `locationKeys` return an
   empty list, even if other middleware set `req.context`.
10. **SSO session start:** an SSO session's lifetime is measured from before the Portal
    redemption, so it never outlives the Portal's handle.

## 2. Production data check (read-only)

The stricter validators reject a whole response when one row is bad. Before tagging, count the
rows in the Portal's production PostgreSQL database that would be rejected. Running the check
needs production database access, so Matt, or someone with that access, runs it. Everyone else
reads only the counts.

### Schema basis

The table and column names come from `SCHEMA_MIGRATIONS` in `src/database.ts` on
mule-portal `origin/main` at `608b090`, where `CURRENT_SCHEMA_VERSION` is 8:

- **Migration 1:** `users` (`email` primary key, `last_login TEXT`); `people` (`email`
  references `users`, `role TEXT` with no CHECK, `all_locations`, `ctx_version`); `locations`
  (`id` identity primary key, `key TEXT NOT NULL UNIQUE`, `name TEXT NOT NULL`); `role_apps`
  and `person_app_overrides` (`app_key`).
- **Migration 2:** `person_app_permissions` (`app_key`, `permission`).
- **Migration 7:** `locations.is_mule BOOLEAN NOT NULL`. This needs no check, because the
  column is always a boolean.
- **Migration 8:** `person_additional_roles` (`role` with `CHECK (role IN ('finance'))`).

`src/identity.ts` maps these tables to what the connector validates:

- The context's `email` is `people.email`. The directory's `email` and `last_login` come from
  `users`, not `people`.
- `locations` is `"all"` exactly when `people.all_locations` is true.
- `is_admin` is true exactly when `people.role = 'ops'`.
- A directory includes only people on an allowed domain whose effective apps include the
  calling app.

Constraints already rule out L3, L4 and R2 below. They are counted anyway as a cheap
confirmation.

### The SQL

Run it with `psql -X -v ON_ERROR_STOP=1 -f preflight.sql` against the Portal's production
database. It runs in a `READ ONLY` transaction and ends in `ROLLBACK`. Part 1 returns counts
only. Part 2 returns each distinct `last_login` value that is not strict ISO-8601, as a JSON
string, with its row count. Neither part returns an email.

Save the SQL from the raw file, not by copying the rendered page. The block is ASCII-only:
the whitespace it looks for is written as regex escapes, so the client encoding cannot change
it. Use the merged commit that holds this file, for example `origin/main`:

```sh
git show origin/main:docs/release/v0.3.0-preflight.md \
  | awk '/^```sql$/ { f = 1; next } /^```$/ { f = 0 } f' > preflight.sql
LC_ALL=C grep -n '[^[:print:]]' preflight.sql   # must print nothing
```

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '60s';
SET LOCAL lock_timeout = '5s';
SET LOCAL standard_conforming_strings = on;

-- Part 1: counts only. Every failing_rows value should be 0.
WITH js AS (
  -- The whitespace JavaScript's \s and String.prototype.trim() remove
  -- (ECMAScript WhiteSpace + LineTerminator), one regex escape per code point,
  -- so the file stays ASCII and the result does not depend on the database
  -- locale or the client encoding.
  SELECT '\t\n\v\f\r\u0020\u00a0\u1680\u2000\u2001\u2002\u2003\u2004\u2005\u2006\u2007\u2008\u2009\u200a\u2028\u2029\u202f\u205f\u3000\ufeff'::text AS ws
), rx AS (
  SELECT '^[' || ws || ']|[' || ws || ']$' AS edge_ws,
         '^[^' || ws || '@]+@[^' || ws || '@]+$' AS email_ok,
         '^[0-9]{4}-(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[01])T([01][0-9]|2[0-3]):[0-5][0-9]'
           || '(:[0-5][0-9](\.[0-9]+)?)?(Z|[+-]([01][0-9]|2[0-3]):[0-5][0-9])$' AS iso
  FROM js
)
SELECT seq, check_id, description, failing_rows
FROM rx, LATERAL (VALUES
  (1,  'L1', 'locations.key empty or with leading/trailing whitespace',
       (SELECT count(*) FROM locations WHERE key = '' OR key ~ rx.edge_ws)),
  (2,  'L2', 'locations.name empty',
       (SELECT count(*) FROM locations WHERE name = '')),
  (3,  'L3', 'locations.key duplicated (extra rows)',
       (SELECT count(*) - count(DISTINCT key) FROM locations)),
  (4,  'L4', 'locations.id duplicated (extra rows)',
       (SELECT count(*) - count(DISTINCT id) FROM locations)),
  (5,  'L5', 'locations.id below 1',
       (SELECT count(*) FROM locations WHERE id < 1)),
  (6,  'E1', 'users.email not lowercase',
       (SELECT count(*) FROM users WHERE email <> lower(email))),
  (7,  'E2', 'users.email fails the connector email pattern',
       (SELECT count(*) FROM users WHERE email !~ rx.email_ok)),
  (8,  'E3', 'users.email duplicated ignoring case (extra rows)',
       (SELECT count(*) - count(DISTINCT lower(email)) FROM users)),
  (9,  'E4', 'people.email not lowercase',
       (SELECT count(*) FROM people WHERE email <> lower(email))),
  (10, 'E5', 'people.email fails the connector email pattern',
       (SELECT count(*) FROM people WHERE email !~ rx.email_ok)),
  (11, 'E6', 'people.email duplicated ignoring case (extra rows)',
       (SELECT count(*) - count(DISTINCT lower(email)) FROM people)),
  (12, 'R1', 'people.role outside ops|franchisee|gm|manager|chef',
       (SELECT count(*) FROM people
         WHERE role NOT IN ('ops', 'franchisee', 'gm', 'manager', 'chef'))),
  (13, 'R2', 'person_additional_roles.role other than finance or hr',
       (SELECT count(*) FROM person_additional_roles WHERE role NOT IN ('finance', 'hr'))),
  (14, 'S1', 'people: ops with all_locations false',
       (SELECT count(*) FROM people WHERE role = 'ops' AND NOT all_locations)),
  (15, 'S2', 'people: non-ops with all_locations true',
       (SELECT count(*) FROM people WHERE role <> 'ops' AND all_locations)),
  (16, 'V1', 'people.ctx_version below 1',
       (SELECT count(*) FROM people WHERE ctx_version < 1)),
  (17, 'A1', 'app keys or permissions empty or with leading/trailing whitespace',
       (SELECT (SELECT count(*) FROM role_apps
                 WHERE app_key = '' OR app_key ~ rx.edge_ws)
             + (SELECT count(*) FROM person_app_overrides
                 WHERE app_key = '' OR app_key ~ rx.edge_ws)
             + (SELECT count(*) FROM person_app_permissions
                 WHERE app_key = '' OR app_key ~ rx.edge_ws
                    OR permission = '' OR permission ~ rx.edge_ws))),
  (18, 'T1', 'users.last_login present but not strict ISO-8601',
       (SELECT count(*) FROM users
         WHERE last_login IS NOT NULL AND last_login !~ rx.iso))
) AS checks(seq, check_id, description, failing_rows)
ORDER BY seq;

-- Part 2: only matters if T1 is not 0. Every distinct last_login value that
-- is not strict ISO-8601, as a JSON string, with its row count. No emails.
SELECT to_json(last_login) AS value, count(*) AS rows
FROM users
WHERE last_login IS NOT NULL
  AND last_login !~ ('^[0-9]{4}-(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[01])T([01][0-9]|2[0-3]):[0-5][0-9]'
                     || '(:[0-5][0-9](\.[0-9]+)?)?(Z|[+-]([01][0-9]|2[0-3]):[0-5][0-9])$')
GROUP BY last_login
ORDER BY count(*) DESC, last_login;

ROLLBACK;
```

On 2026-10-26 this SQL was run against throwaway PostgreSQL 16 databases built from Portal
migrations 1, 2, 7 and 8:

- **One bad row per check.** L3, L4 and R2 could be seeded only after dropping the `UNIQUE`,
  primary-key and `CHECK` constraints that forbid them in the real schema. Every check counted
  exactly its seeded rows. A key with only an interior space was not flagged.
- **Every whitespace code point.** The database held 50 location keys with one of the 25 code
  points at the start or end, 25 emails with one inside, and two app keys with one at an edge.
  It also held rows that must not be flagged: interior whitespace, Latin-1 letters at either
  edge, and U+0085, U+180E, U+200B and U+2060, which JavaScript does not trim. The counts
  matched JavaScript's `trim()` and `\s` on the same rows (L1 50, E2 25, A1 2).
- **Client encodings.** The output was byte-identical under `PGCLIENTENCODING` `UTF8`, `LATIN1`
  and `WIN1252` on both databases. An earlier version of this block held the whitespace as raw
  characters. It undercounted under `LATIN1` (L1 21 of 50) and failed under `WIN1252`.

The PostgreSQL version of the production database has not been checked.

### Reading the result

The check passes when all 18 counts are 0. If a count is not 0, do not tag until the rows are
repaired or the risk is explained and accepted. Repairing data in the Portal is a separate,
approved change and is not part of this checklist.

| Checks | What the connector does with such a row |
|---|---|
| L1–L5 | Any directory read that includes the location fails as a whole. The context of anyone assigned to it is rejected. |
| E2, E5 | Any directory read that lists the person fails, and their own sign-in and re-checks are rejected. |
| E3, E6 | Any directory read that lists both spellings fails, because the directory rejects emails that differ only in case. |
| E1, E4 | The connector does not reject these on its own. They are listed because the Portal looks people up by lowercased email, so a mixed-case row cannot be resolved consistently, and because a lowercase twin turns it into E3 or E6. |
| R1, R2, S1, S2, V1 | The person's context is rejected, and any directory read that lists them fails. |
| A1 | The context of anyone who can open that app, or who holds that permission on an app they can open, is rejected. A bad permission also fails directory reads for that app. |
| T1 | The connector checks `Number.isFinite(Date.parse(last_login))` on directory entries. |

T1 needs one more step. `Date.parse` accepts more than ISO-8601, so a T1 row is not
necessarily rejected. Two values of the same shape can also differ: `2026-08-01 12:34:56` is
accepted (read as local time) and `2026-13-01 12:34:56` is not. Check every value Part 2
lists, adding your connection options to `psql`:

```sh
psql -X -q -tA -F "$(printf '\t')" -v ON_ERROR_STOP=1 -f preflight.sql \
  | awk -F'\t' 'NF == 2 { print $1 }' \
  | node -e 'for (const line of require("fs").readFileSync(0, "utf8").split("\n")) if (line) console.log(Number.isFinite(Date.parse(JSON.parse(line))) ? "accepted" : "REJECTED", line)'
```

Only `REJECTED` values fail a directory read. Record how many accepted values are not
ISO-8601. An empty string is rejected. If T1 is above 0 but the pipeline prints nothing,
the pipeline failed: run it again, and do not read the empty output as a pass.

To find the rows behind a non-zero count, the person doing the repair runs a second, short
read-only transaction:

- Start with the same `BEGIN READ ONLY` and `SET LOCAL` lines, including
  `SET LOCAL lock_timeout = '5s'`, so the query gives up rather than waits behind a lock.
- Keep Part 1's `WITH` clause unchanged. Replace its final `SELECT` with one that lists the
  rows matching that check's `WHERE` clause: `id, to_json(key)` for a location check
  (`to_json` shows edge whitespace), or `email` for a person check.
- End with `ROLLBACK` as soon as the rows are printed. An open transaction keeps its locks,
  and a Portal schema migration that needs them would wait behind it.

Record counts only. Keep emails out of issues, pull requests and chat.

## 4. Cross-repo proofs on the release commit, then the tag

Run both Portal proofs against a checkout of the release commit before tagging. Each one
records the connector commit it tested, so the tag must go on that same commit. Nothing runs
either proof automatically, because no npm script and no CI step references them (mule-portal
`ARCHITECTURE.md`, item 27). Both are local proofs against synthetic data and touch no

### 4a. Request authority: `scripts/check-hr-connector.mjs`

This proof was added by mule-portal#112.

#### Prerequisites (from the script on mule-portal `origin/main`)

- **Docker.** The script runs `docker inspect mule-hr-scaffold-postgres`, so the `docker` CLI
  must reach a running daemon. The container must:
  - be named exactly `mule-hr-scaffold-postgres`;
  - run image `postgres:17-alpine`;
  - publish container port 5432 only as `127.0.0.1:55437`;
  - accept user `postgres` with password `synthetic-scaffold-only`.

  The script does not create the container. One way to meet these checks, derived from them
  rather than taken from the Portal repo, is
  `docker run -d --name mule-hr-scaffold-postgres -e POSTGRES_PASSWORD=synthetic-scaffold-only -p 127.0.0.1:55437:5432 postgres:17-alpine`.
- **Database URL.** It must be exactly
  `postgresql://postgres:synthetic-scaffold-only@127.0.0.1:55437/portal93_contract`.
  - If `portal93_contract` does not exist, the script creates it and marks it with an
    ownership comment.
  - The script refuses an existing database without that comment.
  - Reruns add new synthetic people.
- **Portal checkout.** Check out the mule-portal commit that the production Portal's
  `/health` reports as `build`. That commit must contain `638bfef`. Run `npm ci` and
  `npm run build`.
  The script imports the Portal's compiled `dist/`, and `pg` and `express` from its
  `node_modules`.
- **Connector checkout.** Check out the release commit by SHA and run `npm ci`, whose
  `prepare` step rebuilds `dist/`. Then confirm that `git status --porcelain` is empty, so the proof tests the
  committed artifact.
- **Environment.** The script starts a child process with a stripped environment and
  `NODE_ENV=test`, and asserts that `RENDER` is unset. The connector talks HTTP to localhost,
  which is allowed outside production and Render. The child process has a 120-second limit,
  and each `git` or `docker` call has 15 seconds.

#### Run

From the Portal checkout:

```sh
node scripts/check-hr-connector.mjs \
  --connector-root <path-to-connector-checkout> \
  --database-url postgresql://postgres:synthetic-scaffold-only@127.0.0.1:55437/portal93_contract
```

The script prints the `PASS` lines and a JSON summary. It writes `evidence.json` and
`output.log` to a new `.tmp-hr-contract-*` folder inside the Portal checkout and prints that
folder's path.

#### Pass criteria

- The script exits with status 0.
- In `evidence.json`, `result` is `"PASS"` and `cases` has 14 entries.
- `evidence.connector.commit` equals the release commit's SHA.
- Each value in `evidence.connector.files` (keys such as `dist/index.js`) equals the SHA-256
  of that file in the release commit. These are the hashes recorded in section 3.
- `evidence.connector.sourceDiffSha256` and `evidence.portal.sourceDiffSha256` are both
  `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`, the hash of an empty
  diff, which means neither checkout had uncommitted `src/` or `public/` changes.
- `evidence.portal.commit` is the Portal revision checked above.

Attach `evidence.json` to issue #11.

### 4b. Cached-mode compatibility: `scripts/check-connector-compatibility.mjs`

This proof drives the default cached mode through the exported async connector, on `pg-mem`,
with no Docker. As committed on mule-portal `origin/main`, it cannot run against the release,
for two reasons:

- It asserts that the connector checkout's `HEAD` equals its hard-coded `CONNECTOR_COMMIT`,
  `57c199b`.
- Its typed-consumer step marks `Context["roles"]` with `@ts-expect-error`. The connector's
  types have had `roles?` since PR #10, so `tsc` stops with TS2578 (unused directive). This
  was reproduced against the `ad09394` types on 2026-10-26, and the same step passes against
  `57c199b`'s types.

Either update both in mule-portal (a separate Portal change) and run it as its header
describes, or record in issue #11 that cached-mode compatibility against the release is
unproven. Section 4a includes one cached-mode case ("default cached consumer remains
scalar-role compatible and denies when its cache expires"), which is only partial coverage.
