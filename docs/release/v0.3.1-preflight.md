# v0.3.1 release preflight

Use this checklist to release `@mule/portal-auth` v0.3.1, from the release commit to fleet
adoption. The release is cut from `main` after PR #15 (SEC-13, merged as `7dd9ab3`) and the
release PR have merged. The release PR sets `package.json` to `0.3.1`. Tracking issue:
mattjohnny/mule-workspace#560 (owner decision: mattjohnny/mule-workspace#406, 2026-11-02).

Complete the sections in order. Tag only at the end of section 4, on the merged release
commit that section 3 checked. No consumer adopts the tag before then.

## 1. Version and release notes

### Why 0.3.1

The only change since v0.3.0 is PR #15. It adds one optional property to `PortalError`
(`portalStatus?: number`) and one optional key to its constructor's `extra` argument, and
sets the existing optional `retryAfterSeconds` on more errors. No export, message, error
class, existing field's type, or sign-in, session or authority flow changes, so code that
compiled and ran against v0.3.0 still does. The one observable difference for existing code
is the serialization and deep-equality output in item 4. An additive change takes the next
patch version.

### Release-note items

1. **Sign-in redemption errors carry the Portal's status.** When the Portal answers
   `signInWithPortalToken`'s redemption with a non-2xx status, the thrown `PortalError` has
   `portalStatus` set to that status, `403` included. A throttled sign-in reads
   `portalStatus === 429`; a bad, expired or replayed link reads `401`, `404` or similar. A
   `401` can also mean the Portal rejected this app's own service credential.
2. **Retry-After on redemption 429 and 503.** On a redemption `429` or `503` with a
   whole-seconds `Retry-After`, the error also has `retryAfterSeconds`, clamped to 1–300 (the
   rule context lookups already used). An HTTP-date or malformed value leaves it absent.
3. **Absent, not `undefined`.** On a redemption error, `portalStatus` is absent when the
   Portal sent no status (transport failure, local configuration, a `2xx` that failed
   validation), and `retryAfterSeconds` is absent when there was no whole-seconds
   `Retry-After` on a `429` or `503`. `portalStatus` is also absent on every non-redemption
   Portal call. `retryAfterSeconds` keeps its v0.3.0 behaviour on context lookups, where
   `requireAuth` and `requireAdmin` already read it.
4. **Serialization and deep-equality change.** Where present, `portalStatus` and
   `retryAfterSeconds` are own enumerable numeric properties of the error. A consumer that
   serializes a `PortalError` (`JSON.stringify`, `res.json(err)`, structured logging of the
   whole object) or deep-compares one (`assert.deepStrictEqual`, snapshot tests) sees the new
   keys on failed redemptions. Checker mattjohnny/mule-workspace#555 read all 14 consumers'
   `main` on 2026-11-02: none serializes, spreads or deep-compares a `PortalError`, and none
   reads `portalStatus`, `retryAfterSeconds` or `err.status` from one. So no current consumer's
   behaviour changes by adopting this release.
5. **The field is not called `status`.** Express and `http-errors` read `err.status` as the
   response code. An unhandled sign-in error still answers `500` through Express.

### Unchanged in this release

For every status, the error's message, `name`, class (`instanceof PortalError`), `signedOut`
and `unavailable` are the same as in v0.3.0. A `429` is still not an outage, so it never opens
offline-admin access, and nothing retries. Transport (HTTPS in production, no redirects),
validation, request authority, cached mode, sessions and directory reads are untouched.

### Note for consumers that use the new field

The Portal's redemption limit is per app, so anyone can induce a `429` by flooding forged
tokens. An app that stops counting `429` against a per-caller failure gate needs another
per-caller bound (README, the sign-in redemption paragraph). Daily Close's adoption
(mattjohnny/mule-workspace#553) must keep its per-caller and global redeem budgets ahead of
the redeem and test them.

Not needed for this release. Section 2 of

## 3. Release commit

1. In the release PR, set `package.json` and `package-lock.json` to `0.3.1`. Update the
   README's install example and release-gate paragraph. Check that the release notes above
   still match the code. `dist/` does not change, because no `src/` file does.
2. On the merged release commit, run each of these in sequence, never concurrently:
   - `npm ci --include=dev`
   - `npm run typecheck`
   - `npm test`
   - `node scripts/verify-authority-mutations.mjs`
   - `node scripts/verify-c2-mutations.mjs`

   Then confirm that `git status --porcelain --untracked-files=all -- dist` prints nothing,
   so the fresh build matches the committed `dist/`. This is the check CI runs
   (`.github/workflows/ci.yml`). Plain `git status --porcelain` is not empty here, because
   the mutation scripts write untracked `docs/evidence/authority-mutations-*` and
   `docs/evidence/c2-*` folders.
3. Record `sha256sum dist/*` for that commit.

## 4. Tag

The v0.3.0 cross-repo Portal proofs (its section 4) are not rerun for this release. They
prove request authority and cached-mode compatibility against the Portal, which PR #15 does
not touch. The redemption change is proved by `test/redeem-status.test.js` against a real
localhost Portal stub and Express, inside `npm test`.

When section 3 passes on the merged release commit:

1. Tag that commit `v0.3.1` and push the tag.
2. Confirm that `git rev-parse v0.3.1^{commit}` equals the commit section 3 checked.
3. Publish the GitHub release for the tag, as for v0.3.0.
4. Keep the section 3 results and hashes on the tracking issue.

## 5. Consumer adoption

The fleet standard (mule-fleet-docs `standards.md`, item 18) is that every consumer upgrades
within a week of the tag. The owner decision for this release is all 14 apps within the
2026-11-02 daily-close run. For each app:

- [ ] Run `npm install github:mattjohnny/mule-portal-auth#v0.3.1` (not only `npm pkg set`),
      so `package.json` and the lockfile both move.
- [ ] In `package-lock.json`, check `node_modules/@mule/portal-auth`: `version` is `0.3.1`
      and `resolved` ends in `#<tagged commit SHA>`.
- [ ] The installed `node_modules/@mule/portal-auth/dist/index.js` and `dist/portal.js`
      hashes match section 3.
- [ ] Any app test that pins the connector's version, resolved commit or a `dist` hash is
      updated.
- [ ] The app's own full verification passes. After deploy, its `/health` `build` matches the
      merged commit. Where the anonymous `/health` omits `build`, use a signed-in `/health`
      or the Render deploy API.

Only Daily Close changes its own code to use the new field (mattjohnny/mule-workspace#553).
The other 13 apps need only the pin and lockfile bump.

After the adoptions, update the `@mule/portal-auth` row of the shared-library version matrix
in mule-fleet-docs `roster.md`.
